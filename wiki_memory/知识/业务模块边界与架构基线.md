## 目标结构与过渡规则

方向性结构如下；只有已有职责并实际落地时才创建目录：

```text
src/
  app/                       应用装配与跨域协调
  features/
    collection/              收藏、站点地址、收藏搜索
    groups/                  分组管理与排序
    github/                  作者、仓库导入与刷新
    history/                 浏览历史
    data-transfer/           备份与导入导出
    appearance/              设置、主题、壁纸、字体
  shared/                    确有跨域价值的 UI 与纯工具
  platform/                  浏览器、存储与资产适配
  popup/                     扩展 popup 装配
  data/                      默认数据与选项
  main.tsx / background.ts   主入口与后台桥
```

- `app` / `popup` 装配业务、共享 UI 和平台接口；跨工作区导航、设置预览与确认后提交由装配层协调。计算规则留在所属业务，不通过新增全局状态串联。
- `features/<业务>` 可依赖同业务与 `shared`；使用 `platform` 或其他业务时，先明确公开文件、API、消费者和理由，不访问对方私有实现。新模块不反向读取旧 `components/hooks/lib` 混合实现或装配入口。
- `shared` 不反向依赖业务、页面或装配；不能只因 popup/导入也调用就把收藏去重规则改名为通用工具。`platform` 可依赖共享基础，不依赖业务界面/Hook/App；存储适配与业务变换不得相互嵌套。
- 纯业务计算不访问 React Hook、浏览器存储或网络。需要副作用时由调用方传入数据，窄 API 返回结果；优先命名文件入口，避免巨型 `index.ts` barrel 和循环重导出。
- 保留现有 `components/hooks/lib` 为过渡目录；旧消费者可以继续通过兼容导出调用已提取模块。每次按共同变更动因提取一个内聚边界，先核全部调用方、兼容测试和实际依赖图，再逐步改消费者。不批量迁移导入路径，不创建空壳目录。
- 守卫实际门槛：新 `features/shared/platform` 的运行时与类型边均检查；同层允许，feature/platform 到 shared 允许，`src/types.ts` **仅纯类型**引用为精确过渡许可。其他跨业务/平台入口须在脚本 `publicContracts` 精确登记 from/to 与理由；当前登记为空。旧混合目录边只报告；全图运行时循环直接失败，类型循环独立报告。无文件行数门槛。
- 运行时代码、测试和局部样式按职责就近；现有样式先保持入口与层叠顺序。`main.tsx` 的 `styles → wallpaper-glass → typography → text-selection` 和 popup 独立样式入口均需保护，不能凭 TS 图认定 CSS 可自由移动。

## URL 提取边界与后续选择

七个函数及私有 `knownSiteNames` 原样迁入收藏model；导航URL与保守比较键是收藏领域契约，书签/备份/popup是其消费者，历史仅复用主机与名称推断，因此本轮选择 `features/collection`，没有创建重复的 shared URL 实现。图证据是原 site-utils 的16个运行时调用模块保持原入口，新模块只增加一条类型出边；`github-workspace` 原重导出也保持。`comparableSiteUrl` 仍只比较，不能写回导航地址；没有新增state字段/迁移或改变存储键。favicon、搜索评分、拖拽、排序、GitHub导入及存储逻辑均留原位。

后续最多三个小范围候选：① site-utils 的分组重排规则，先固定保护组与工作区域接口；② App 中GitHub批量刷新来源去重/报告组装的纯计算，网络和状态提交仍由装配协调；③ data-transfer 中单组便携格式校验，先保持旧格式、错误信息与完整备份解析互通。每次仍独立回归。App整体、storage迁移链与玻璃样式具有跨域生命周期/兼容/绘制契约，不以本次目录治理直接拆开。

## 已确认的决策

- 交付形态定为 Manifest V3 浏览器扩展并接管新标签页，而不是继续以网页形式"设为启动主页"。讨论轮明确了两者的本质差别：普通网页只能作为启动时打开的主页，真正替换新标签页必须走扩展。被否决的备选一是 PWA 安装，被否决的备选二是仅设为启动主页，理由都是无法接管新标签页。
- 明确并向用户说明平台硬限制：Chrome/Edge 自带新标签页搜索框无法被嵌入或保留，浏览器不允许网页访问那块原生界面；顶部地址栏仍是原生的。
- 搜索行为改为调用浏览器当前默认搜索引擎，而不是在代码里写死某一家。被否决的方案是硬编码 Google/Bing/百度三选一，理由是那样用户改了浏览器默认搜索引擎，扩展不会跟随。
- 双运行环境采用适配器隔离：扩展模式走扩展本地存储，网页模式继续走 localStorage 与既有存储键；收藏数据版本与既有逻辑保持不变。被否决的方案是两端共用同步读取，理由是扩展存储天生异步，同步路径会导致默认数据闪烁或误覆盖扩展中已有数据。
- 跨环境迁移用 JSON 导入导出解决：导出带格式标识与时间戳，导入先校验再二次确认，确认后整体替换，格式错误则完全不改动现有数据。被否决的是"自动双向同步"，理由是本地无后端，冲突无法仲裁。
- 第一版采用本地"加载已解压扩展"安装，不发布到 Chrome Web Store 或 Edge Add-ons；Chrome 与 Edge 共用同一套源码与构建产物；无痕窗口不接管新标签页，属平台限制并如实说明。

## 检查与操作

- 检查当前部署形态：确认仍是普通 Vite 网页，依赖本机开发服务器端口启动，既没有 PWA 配置也没有扩展配置。
- 核对官方能力边界，确认两点后才写入方案：扩展可通过默认搜索接口直接调用浏览器当前默认搜索引擎；新标签页可通过 MV3 的新标签页覆盖字段接管。
- 检查现有状态持久化入口，确定在不破坏网页版的前提下切换到扩展存储的插入点。
- 新增扩展构建模式，配置新标签页接管与最小权限集。

```
chrome_url_overrides.newtab  → 接管新标签页
permissions: search, storage
静态资源使用相对路径 → 扩展可完全离线启动
产物：可加载的扩展目录 + 可分发 ZIP
```

- 把现有搜索框改为双用途：输入时实时筛选当前分组收藏，按回车走浏览器默认搜索引擎在当前标签页搜索，空内容回车不执行；提示文案改为"搜索网页或筛选收藏"；普通网页模式下回车使用 Google 作为兼容回退。
- 新增搜索适配器，优先调用扩展默认搜索接口并指定在当前标签页打开。
- 新增异步存储适配器，统一暴露读取、保存、导出、导入四个动作。
- 把状态加载改为异步初始化，加载完成前显示轻量占位，避免闪出默认收藏或覆盖扩展中已有数据。
- 在管理区域接入"导出数据"与"导入数据"，导出体固定为带格式标识、导出版本、导出时间与完整状态的结构。

```
format: "site-hub-export"
exportVersion: 1
exportedAt
state: SiteCollectionState
```

- 排查首次构建失败：根因是 Windows PowerShell 执行策略拦截了 npm 的 PowerShell 包装脚本，代码尚未开始编译；改用系统自带的 npm 命令脚本继续验证，未修改用户系统设置。
- 补测试并锁住三个易回归点：回车必须调用浏览器默认搜索、扩展存储不能与网页存储混用、导入文件必须先校验再覆盖。
- 排查交互测试失败：根因是逐字模拟包含中文与回车键的输入时只写入了首字符，表单逻辑本身没有报错；改为直接设置完整查询再提交表单，从而准确验证真正关心的搜索调用。
- 产物验收：确认 ZIP 内清单文件位于压缩包根目录，扩展 HTML/CSS/JS 均使用相对路径，可离线加载。
- 跑完整端到端回归，确认网页版的拖拽、筛选与响应式未被新功能影响。
- 编写并交付 Chrome/Edge 的最短安装步骤文档。

## 问题、结果与下一步

- 结果：同一套源码支持网页与扩展双模式构建，扩展安装后新标签页自动显示收藏主页；搜索跟随浏览器默认搜索引擎；扩展数据走扩展本地存储，网页版继续兼容原有键；JSON 导入导出打通两端迁移；Chrome 与 Edge 共用同一扩展包。

## 已确认的决策

1. 判定该现象本质是「自动图标」选择逻辑的缺陷，而非 Wikipedia、Kimi 等具体站点图标本身损坏或缺失。
2. 同一站点在 Edge 与 Chrome 自动结果不同，根因定位为两浏览器各自独立的 favicon 缓存、访问记录与默认占位图样式不一致，而非源码按浏览器差异化处理。
3. 否决「站点图标源损坏」假设：用户截图中的白页/地球并非目标站点的真实 favicon，而是浏览器在未命中缓存时回退的通用占位图。
4. 确认当前自动流程把浏览器本地 `_favicon` 放在第一顺位，应作为「待验证候选」而非「最终可信结果」处理。
5. 临时缓解方案确定为引导用户手动切换「网站 / 高清 / 品牌」来源，不依赖自动链路。
6. 彻底修复方向拍板：识别到通用占位图（白页、地球）后必须继续降级尝试后续来源，且只缓存被判定为真实有效的图标结果。

## 检查与操作

1. 读取用户提交的 Edge 与 Chrome 两张自动图标截图，比对二者视觉差异：Edge 显示白色文件页、Chrome 显示灰色地球。
2. 检查「自动」图标的来源选择顺序逻辑，确认浏览器本地 `_favicon` 处于优先级最高位。
3. 梳理扩展环境下 favicon 获取链路：本地缓存优先 → 网站原图 → 高清 → 品牌图标，逐层降级。
4. 核对 Chromium 对未命中 favicon 网址的官方回退行为，确认浏览器仍会返回一张「加载成功」的通用占位图。
5. 阅读 `site-utils.ts` 第 124 行附近的成功判定分支，确认当前仅校验图片是否成功加载与尺寸是否达标。
6. 阅读 `favicon.tsx` 第 126 行附近的结果缓存逻辑，确认占位图一旦通过尺寸校验即被当作成功结果写入缓存。
7. 对照官方 `_favicon` 接口说明（Chrome 扩展 favicon 文档），确认该接口返回占位图时不会显式报错或标注占位。
8. 分析 Edge 与 Chrome 缓存互独立的事实：两浏览器对同站点的本地 favicon 命中情况不同，导致回退占位图样式不同。
9. 推断「白页 vs 地球」差异来自浏览器各自的默认占位图绘制，而非站点数据差异。
10. 验证降级链被提前截断：因占位图通过加载/尺寸校验，后续「网站、高清、品牌」来源未被执行。
11. 评估临时方案可行性：手动选择能绕过自动链路，直接确认非源码按浏览器分叉。
12. 记录关键代码锚点，便于后续修复直接定位判定与缓存两处。

## 问题、结果与下一步

根因结论：自动图标逻辑把浏览器本地 `_favicon` 视作第一顺位可信来源，但其成功判定只检查「是否加载成功 + 尺寸是否达 64px」，无法识别浏览器在未命中缓存时回退的通用占位图（Edge 白页 / Chrome 地球）。占位图通过校验后即被缓存为最终结果，导致后续「网站 / 高清 / 品牌」降级源被提前截断。Edge 与 Chrome 结果不同，源于两浏览器独立的 favicon 缓存、访问记录与默认占位图样式，并非源码按浏览器差异化处理。

下一步修复方向：
- 将浏览器 `_favicon` 结果标记为「待验证候选」，引入占位图识别（白页/地球灰度指纹或尺寸/色彩特征比对），命中占位则继续降级。
- 调整 `site-utils.ts` 第 124 行附近的成功判定，增加占位图排除条件。
- 调整 `favicon.tsx` 第 126 行附近的缓存逻辑，仅缓存被多级校验确认为真实有效的图标。
- 统一跨浏览器体验：无论底层占位图样式如何，自动链路都应在真实图标缺失时一致回退到品牌/首字占位而非浏览器默认占位。
- 临时仍建议用户用「网站 / 高清 / 品牌」手动来源作为 workaround。

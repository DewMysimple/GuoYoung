# 工作流与记忆维护

[[Wiki/MOC_项目知识|← 返回项目知识 MOC]]

本页规定 Mysimple 工程的记忆分层与每轮协作中如何维护 Wiki，确保更换会话 / Agent 后工程记忆不丢失。

## 记忆分层

- **事实层**：源码、测试、配置、锁文件与脚本是工程事实来源；当前基线必须对应实际验证结果。Wiki 与之冲突时，当轮修正 Wiki。
- **事件层**：`Wiki/日志/` 是不可改写的流水账，记录每轮发生了什么。封存后不改写，更正须新增轮次。
- **知识层**：除日志以外的 `Wiki/`（主题页、ADR、MOC、状态页）是可修订的沉淀，记录跨会话有效的架构、接口、约束、状态与已确认决策。

## 每轮启动（4 步）

1. 读 `AGENTS.md`（工程专属硬约束）。
2. 读 `Wiki/MOC_项目知识.md` 与 `Wiki/当前状态.md`。
3. 按任务只读相关主题页 / ADR / 少量日志，**不默认加载全部历史**。
4. 用源码核实关键事实；与 Wiki 冲突时以代码为准并当轮修正。

## 执行授权

- 用户明确要求实现、修复或维护，即在本次任务范围内执行。复杂任务说明步骤并持续汇报，不等待固定口令或重复计划确认。
- 用户要求“只讨论 / 先计划”时遵守该范围；只有影响目标的必要缺失信息或范围外不可逆操作才具体确认。
- 旧 ADR-011 已由 [[Wiki/决策/ADR-013|ADR-013]] 取代；旧日志里的等待指令只描述当时的流程，不作为现行门禁。

## 记忆写入边界

- 完成一轮有实质交付（功能、修复、UI、讨论结论、测试、维护）后，写对应分类的一篇日志。
- 只有跨会话有效的架构 / 接口 / 约束 / 状态、已确认决策及其后果、反复踩坑，才沉淀进知识层。
- 一次性问答、临时调试不进 Wiki。

## 写入流程

1. 判定六类之一，取其分类目录内最大编号 +1。
2. 复制 `Wiki/日志/README.md` 模板，填 8 个元数据字段（**无 frontmatter**）。
3. 写五个固定二级标题章节，信息密度集中在「检查与操作」。
4. 在总 MOC 与所属分类 MOC 各登记一次（表格内别名用 `[[路径\|别名]]`，竖线必须转义）。
5. 跑 `npm run lint:wiki` 直至通过。

## 时间字段规则

- 历史日志（源自原轮次 001-041）：时间为重建值，从 `22:55:36` 起每分钟 +1，时间行内联标注「重建值·源自原轮次 X-Y」。
- 历史日志（源自原轮次 042-045）：保留真实导出时间，不标注。
- **此后新日志一律用真实北京时间，不再回填**（见 `Wiki/日志/README.md` 时间字段口径）。

## Git 交付约束

- 当前 GitHub 仓库为 [`DewMysimple/GuoYoung`](https://github.com/DewMysimple/GuoYoung.git)，本地远程名固定为 `origin`。
- 本轮只要产生文件修改，就必须在完成验证后创建 Git commit，并将当前分支推送到 `origin`；不允许留下未提交或未推送的本轮改动再交付。
- Agent 负责执行本地提交和远程分支推送；发布标签是否推送按具体发布任务执行。涉及 GitHub Release 时，按发布流程完成提交、分支推送和明确要求的版本标签推送。

## 冲突与过期

- 知识页与代码冲突：以代码为准，当轮更新知识页并 bump `updated`。
- ADR 被推翻：新增 ADR 标注 `supersedes`，旧 ADR 标 `superseded_by`，双向链接，旧 ADR 正文不改写。
- 日志不更新；更正走新增轮次。

## 校验命令

    npm run lint:wiki

校验结构、链接可达性、知识页 frontmatter、日志五章节与编号连续、MOC 排序、源轮次覆盖率、时间戳唯一性。
